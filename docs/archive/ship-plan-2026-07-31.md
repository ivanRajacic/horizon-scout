# Ship plan and landscape notes - 2026-07-31

Written after the 2026-07-31 planning conversation. This is the orientation doc for
finishing Horizon Scout and shipping it: what was decided, what the research found
about where this project sits in the field, what the eval actually costs, and the
judge decision that is still open. `working-plan.md` and `horizon-scout.md` have NOT
yet been updated to record the descope below - that is a step, not a done thing.

---

## 1. The decision in one paragraph

The full study (four retrieval conditions x full bank, all judged, plus Study 2 and
the agentic condition) is descoped. The retrieval stack is collapsed to
hybrid + rerank, chosen on the evidence of the 2026-07-29 ladder run. The bank gets
finished route by route, the adversarial and ambiguous skills get flipped into the
batch orchestrator, and the judge moves off the Max subscription onto a cheap API
(single-digit euros for the whole bank - measured, see section 6). The deliverable
is a write-up that leads with the question-authoring factory, because the landscape
research (section 4) says that is the part nobody has published.

## 2. Why the descope is safe to make

- The blocker was never money, it was the 5-hour Max window: judging 40 answers ate
  about half of one. On an API the same judging costs ~2-4 EUR for the entire bank.
- The retrieval question already has an answer on record. The 2026-07-29 ladder run
  (10 vector questions x 4 conditions, ranking metrics off gold_project_ids,
  deterministic and nearly free): hybrid_rerank leads recall@20 at 0.875 and every
  condition's ranking is in `data/runs/ladder-2026-07-29/report.md`. The RQ2
  crossover is visible too: lexical recall@20 collapses 0.890 -> 0.522 from
  exact-term to paraphrase while dense holds 0.872 -> 0.807.
- SQL questions never touch the LLM judge (scored by executing the generated SQL
  against gold - free). Adversarial questions go to the one-call rubric overlay,
  not six-call RAGAS. So "judge the full bank" means ~80-90 RAGAS-judged answers,
  not 113.

## 3. What is actually in this repo (the inventory)

- **A working QA system** over CORDIS: 35,389 projects in DuckDB, 190,248-vector
  FAISS index, four retrieval conditions behind one interface (BM25 / dense /
  RRF hybrid / cross-encoder rerank), guardrailed text-to-SQL, router
  (sql / vector / scoped), synthesis, full tracing (every prompt versioned AND
  content-hashed, every run logged with cost).
- **An evaluation harness**: two runners (`run-bank` varies the router,
  `run-retrieval` varies the retriever), checkpointed and resumable, reports
  generated from append-only records. Deterministic scoring wherever a right
  answer exists; RAGAS + refusal rubric only for answer quality; every LLM call
  priced at the one transport gate.
- **A bank of 48 execution-verified questions** (of a planned ~113 - `gap-report`
  has the live per-cell numbers). Every gold answer proven by execution at
  authoring time. Two human-gated append paths only; never hand-edited (one
  recorded exception, vec-28, on explicit instruction).
- **The multi-agent authoring factory** - the distinctive piece. Two pipelines
  (`/question-orchestrator` for drafting, `/explore-corpus` for corpus mapping)
  built on four principles arrived at through four audit rounds:
  - Split authority: drafter authors facts; critic attacks and reports typed
    findings with NO verdict and no kill power; a separate judge rules
    UPHELD/DISMISSED on every finding before ACCEPT/FIX/ABANDON; the orchestrator
    is a message bus that judges nothing.
  - Deterministic-first: anything with a right answer is code (id assignment,
    validation, cross-checks, report generation, 100% re-execution of evidence).
  - Typed append-only journals as the only state; canonical outputs generated by
    code from the journal, never written by a model; killed runs keep finished work.
  - Read-only subagents by construction, bounded budgets, human-gated promotion.
- **The paper trail**: research design (`horizon-scout.md`), execution state
  (`working-plan.md`), two pipeline audits with measured before/after
  (`docs/archive/`), numbered optimization plans (`optimization/`).

## 4. Where this sits in the field (research round 1, five parallel searches, 2026-07-31)

### 4a. The QA system itself: commonplace

Router over text-to-SQL + vector + filtered-vector is a LlamaIndex tutorial from
Oct 2023 (`SQLAutoVectorQueryEngine`). Hybrid + rerank is called the "minimum viable
baseline" in 2026 practitioner writing. Filtered ("scoped") vector search is a
shipped feature of every vector store, with its own systems literature (ACORN,
SIGMOD 2024). Guardrailed read-only SQL is the recommended standard control.
Verdict: table stakes, competently assembled. Present it as the instrument, not the
contribution. Notable gap on the academic side that the bank speaks to:
RAGRouter-Bench (arXiv 2602.00296, Jan 2026) benchmarks adaptive-RAG routing but
has NO SQL/structured route; SynTQA (2409.16682) routes but has no adversarial
cells. A bank with per-question gold routes measures exactly the oracle-vs-router
gap that line of work names as open.

### 4b. The eval design: current best practice, ahead in three spots, one named gap

"Deterministic-first, LLM judge only where unavoidable" is now consensus advice
(Hamel Husain's eval guide, Braintrust, DeepEval 2026: "the LLM judge is your
fallback, not your default") - but it is weakly practiced in the wild. Genuinely
uncommon things this repo does:

1. SQL execution accuracy as an eval cell inside an application harness (normally
   confined to text-to-SQL papers, BIRD/Spider-style).
2. Adversarial gold that is an absence PROVEN by executed sweeps.
3. Per-call priced cost telemetry driving architecture. The EvalEval Coalition
   post ("AI evals are becoming the new compute bottleneck", Apr 2026) argues
   almost nobody reports eval cost at all. The measured 10x-ish judging vs
   generation figure appears to be an unpublished data point.

The named gap: the Sonnet judge was never validated against human labels
(Hamel's TPR/TNR protocol; "Reliability without Validity", arXiv 2606.19544, calls
it the Minimum Viable Validation Protocol). The judge swap in section 7 partially
answers this - report agreement numbers against the frozen Sonnet verdicts.
Secondary gaps worth one disclosure line each in the write-up: no over-refusal
check on answerable questions (CReSt's point, arXiv 2505.17503), and no formal
coverage argument for the bank's question distribution.

### 4c. The verified bank: the distinctive piece

- Mainstream synthetic-benchmark tools verify little or nothing: RAGAS testset
  generation has no validation step; DataMorgana (arXiv 2501.12789) sample-audited
  ~200 questions and "decided not to focus on fidelity"; YourBench (2504.01833),
  the best of them, still ships ~15% invalid questions after filtering.
- DataMorgana PUBLICLY DROPPED unanswerable questions because they could not
  guarantee absence in a large corpus. The ADV protocol here proves absence by
  execution - the exact thing they gave up on.
- Jan 2026 audit (arXiv 2601.08778): BIRD Mini-Dev is 52.8% wrong, Spider 2.0-Snow
  62.8% wrong; corrections move leaderboard rankings up to 9 positions. KGQA
  datasets average ~57% correct (2505.23495). The two canonical "human-verified"
  SQL benchmarks failed the year this bank was built.
- Closest published analogue to live-DB-grounded authoring: KGQAGen (in
  2505.23495) - executes SPARQL post-hoc, no human gate, sample-audited at 96.3%.
- Verdict from the search: every ingredient exists somewhere; the combination
  (live-tool-grounded authoring + execution-verified gold + absence-by-sweep +
  per-item human gating + deterministic prechecks) appears unpublished. Framing:
  the code-domain verification standard applied to a retrieval corpus, in the year
  the field learned its benchmarks are half wrong.

### 4d. The multi-agent architecture: converged on the 2026 zeitgeist, past it in one place

- The field named this space "harness engineering" in early 2026 (OpenAI post;
  "Agent = Model + Harness"). The four principles in section 3 map onto it.
- "Separate evaluator from generator" is common wisdom. The three-way split -
  critic with no kill power, separate judge ruling per finding - is rare; the
  search found essentially one commercial doc (DevMatrix) with the same shape.
  The motive is now measured: judges are up to ~50% likelier to wrongly pass
  their own work (arXiv 2604.22891 and related); separating generation from
  review is worth ~20% (survey 2508.16665).
- Typed domain journals with code-generated canonical outputs: not a discussed
  pattern anywhere the search looked (the event-sourcing literature is about
  runtime state, not domain state).
- "Establishing Best Practices for Building Rigorous Agentic Benchmarks"
  (arXiv 2507.02825) prescribes close to exactly what was built here.

### 4e. CORDIS: open territory

- A decade of network-analysis/KG papers on this corpus; zero QA benchmarks over
  CORDIS or ANY research-funding database found. Commercial funding-intelligence
  products (Dimensions, Clarivate, Elsevier, criteri.ai) publish no accuracy
  numbers for NL query.
- Concurrent independent work exists: `tavitatavi/cordis-mcp-server` (GitHub,
  3 commits, Jul 15-17 2026, 0 stars). FastMCP over CORDIS-in-DuckDB, 8 read-only
  tools, guarded run_sql, LangGraph agent, 16-question eval (deterministic routing
  check + Sonnet-judged answers vs SQL-computed ground truth, 15-16/16 over three
  runs). SQL-only - no text/vector side at all, no authoring pipeline, no write-up.
  Cite it as concurrent convergence, not competition. It independently validates
  the corpus + DuckDB + MCP + guarded-SQL shape.
- A public, execution-verified QA benchmark over CORDIS would be first of its kind.

## 5. The write-up framing (what to lead with)

Lead with the factory and the bank; the system is the instrument. The judging-cost
discovery is itself a section: judging measured at ~10x generation per answer at
Anthropic prices, and the eval was restructured so everything with a right answer
is scored by code, with the judge reserved for judgment. The retrieval result is
one table (the 07-29 ladder + the exact-term/paraphrase crossover). Disclosures:
judge validated against Sonnet agreement rather than human labels; bank at the
size it froze at; RAGAS 0.4.3 with the one-paragraph NLI amendment, not stock.

## 6. What the eval costs (measured, then priced)

Ground truth from `data/runs/ladder-2026-07-29/records.jsonl` (160 executed
answers, 40 of them judged - 10 questions x 4 conditions):

| thing | measured |
|---|---|
| generation, per answer | 1 call, ~17k in / ~1k out, $0.028 (Haiku) |
| judging, per answer | 6 RAGAS calls, 110,419 in / 9,349 out, $0.48 (Sonnet) |
| whole run | $23.56 priced, of which $19.02 judging |

Input/output split is 92/8. The 6-calls-per-answer multi-call RAGAS behavior is IN
these numbers (usage is logged at the one transport gate all calls pass).

Scaled to the full bank (~113 questions, ~80-90 RAGAS-judged, one condition):
~13-14M judge tokens + ~2M generation. Priced (verified on live pages 2026-07-31):

- DeepSeek V4 Flash ($0.14/$0.28, cache hits 98% off): ~$0.018/answer ->
  **~1.50-2 EUR for the whole bank**.
- gpt-5-mini via Batch API (50% off -> $0.125/$1.00): ~$0.023/answer ->
  **~2-2.50 EUR**. Standard (no batch): ~5 EUR.
- Reference: Haiku 4.5 batch would be ~$27 of real API spend; xAI ~$50 (skip).
- Calibration experiment (both candidates re-judge the 40 existing answers):
  ~1.50 EUR combined.

Pessimism ceiling (~8-10 EUR total): gpt-5-mini reasoning tokens bill as output
(pin reasoning effort to minimal - this is the one real lever), hybrid/L3 contexts
run longer than the measured vector rows (+30-50% input on those), RAGAS parse
retries on a weaker judge (+10-30% calls). Multiple conditions multiply linearly.

Free tiers exist (Mistral claims 1B tokens/month, unverified; Baseten $30 credit;
Cerebras ~3M/day) but juggling them to save 6 EUR is jerry-rigging - pay the euros.
Warning recorded for later: the Gemini free tier that blogs still quote at 1,500
requests/day was cut to ~20/day in Dec 2025.

## 7. Judge choice (open decision): DeepSeek V4 Flash vs gpt-5-mini

Generation stays Haiku on `claude -p` (Max, ~0 marginal). Only judging moves.
Cross-vendor judge is cleaner than today's all-Anthropic hat stack (Opus authored
questions/references, Haiku generates, judge scores).

**DeepSeek V4 Flash** - for: cheapest; capability unquestioned (AA index rank #2);
`thinking: disabled` pins reasoning off and reasoning lives in a separate field
anyway; temperature 0 allowed; 2,500 concurrent; no batch queue. Against: ZERO
published judge track record for V4 (the 21-judge study, arXiv 2606.19544, froze
pre-V4; predecessor V3.2 was mid-pack: JudgeBench kappa 0.545 vs Sonnet's 0.782,
and third-worst position bias of 21 - partially inert for single-response rubric
scoring); only loose JSON mode (no json_schema); docs admit occasional empty
content; essentially no RAGAS community record - we would be first.

**gpt-5-mini** - for: the strongest direct evidence either has - best of 8 judges
on a 1,248-decision human-adjudicated citation task (F1 0.908, kappa 0.636, above
the human panel's own mean; arXiv 2607.08700, Jul 2026); a second paper found
swapping gpt-5-mini for Sonnet as judge left conclusions unchanged (2605.06308);
OpenAI is RAGAS's home turf (the 4%-vs-40% parse-failure split, issue #1631);
strict json_schema. Against: **deprecated, shutdown 2026-12-11** - a frozen judge
with five months to live (successors are worse trades today: gpt-5.4-mini scored
lower as a judge in the same paper; gpt-5.6-luna has no judge evidence);
temperature is locked at 1 for the whole GPT-5 family (no nominal determinism;
RAGAS needs the temperature=1 config workaround, issue #2440); reasoning bills as
output; OpenAI's own graders feature does not allowlist any GPT-5 model.

The deciding asymmetry: gpt-5-mini has strong evidence and an expiry date;
DeepSeek has no evidence and no expiry date.

**The tiebreak is empirical and costs ~2 EUR:** run both over the 40
already-Sonnet-judged answers; compare agreement with Sonnet and parse-failure
rate (instrument silent Nones - RAGAS returns None on parse failure and a weak
decomposer scores 0.0, not NaN); pick the winner; FREEZE it for the entire study;
report the agreement number in the write-up. Never change judges mid-study.

## 8. The steps, in order

1. **Record the descope** in `working-plan.md` (and the tombstones in
   `horizon-scout.md`): retrieval collapsed to hybrid_rerank on the 07-29 ladder
   evidence; Study 2 ladder and agentic condition dropped; judge swap planned.
2. **Flip `/draft-adversarial-question` and `/draft-ambiguous-question` into
   `/question-orchestrator`.** The skills exist and are orchestration-ready; they
   are only marked "interactive only" in the gap report. Smaller job than it looks.
3. **Finish the bank, day by day**, via `/draft-questions` packets ->
   orchestrator tabs -> ticked report -> `promote-drafts`. `gap-report` drives
   the cells. (Reminder from 07-28: always pass `--model` and `--effort` at tab
   launch; point `wt` at a script, never an inline quoted command.)
4. **Judge swap**: add an OpenAI-compatible backend next to `ClaudeCliLLM` in
   `src/judge/ragas_backend.py` (same `BaseRagasLLM` surface, different base URL,
   its own concurrency - the claude -p semaphore governs only claude -p). Run the
   2-EUR calibration (section 7), pick, freeze, record versions.
5. **Run the bank end to end** on hybrid_rerank + the frozen cheap judge,
   overnight, `--no-judge` first then `--resume` for verdicts (the two-stage shape
   `docs/running-the-bank.md` already documents).
6. **Write it up** per section 5. Cite the concurrent repo. Ship, then stop.
